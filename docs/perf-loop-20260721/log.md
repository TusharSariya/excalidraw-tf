## Iteration-3 research digest — 2026-07-22

Owner ideas (spatial indexing, staggered radial updates, "modern canvas tricks") triggered 3 research agents, converted into the iteration-3 experiment queue below; a further round of research (2 Sonnet web-survey + 2 Codex gpt-5.6-sol project-grounded, plus 2 Sonnet sub-agent spawns covering Figma/Miro and Konva/Fabric.js specifically) broadened and partly validated the findings.

**Spatial indexing / viewport culling** — verdict: NOT useful for the laptop's pan problem (at fit-zoom, culling already returns the whole visible scene — the cost is `drawImage` call volume/compositing, not the O(n) cull scan, which is sub-ms even unindexed). **IS** useful for the genuinely unaccelerated hot paths: `getElementsAtPosition` (`App.tsx:6157`) runs a full-scene geometry hit-test on **every unthrottled mousemove** during hover, and `getElementsWithinSelection` (marquee, `selection.ts:90`) re-scans per drag frame. Design: static uniform grid keyed on `sceneNonce`, result-identical + opt-in (`spatialHitIndex`). **Independently confirmed as the right idea by Excalidraw's own upstream**: open issue [excalidraw/excalidraw#10063](https://github.com/excalidraw/excalidraw/issues/10063) (Oct 2025, unbuilt) proposes the identical quadtree/R-tree fix for the identical O(n) `isElementInViewport` scan, citing lag at 5k-24k elements — matches our 7k-element measurements. Same issue also proposes dirty-region partial redraw + merging the static/interactive RAF loops. Cheap transferable refinements found: tldraw's hysteresis-bounded culling (expand cull bounds ~20%, recompute only on boundary-cross, not every pan frame — open [tldraw/tldraw#7436](https://github.com/tldraw/tldraw/issues/7436)); Fabric.js cached absolute coordinates (`aCoords`/`oCoords` — cheap 2-point transform per frame instead of full recompute); Fabric.js governed cache-size limits (bounds bitmap-cache memory — relevant to our unbounded WeakMap concern); Fabric.js `dirty`/`cacheProperties` whitelist invalidation. **Staggered radial updates** (owner idea) — investigated as a literal feature: time-slice the click-triggered focus-dimming reconcile so it visually sweeps outward from the click point. **Major independent finding (Sonnet, Codex-adjacent)**: the laptop's 54%-dropped-frames pan problem is most likely **GPU compositor tile-pool eviction** (Chrome's `cc`-compositor evicts and synchronously re-rasterizes tiles when a weak iGPU's VRAM budget is exceeded), not a paint-cost or draw-call-count problem per se — which would explain why already-cached bitmaps still jank. Diagnostic recipe: `chrome://tracing` categories `cc`/`viz`/`gpu`/`blink` watching `LayerTreeHostImpl::UpdateTilePriorities`/`SkiaRenderer::PrepareTiles`/`SubmitCompositorFrame`, or the faster DevTools Rendering-tab "Frame Rendering Stats" + "Layer Borders" overlays for live triage without a full trace. OOP-rasterization is now the unconditional Chromium default (140+) — no longer a togglable lever. **Answers our stated "no auto-detect for weak hardware" gap**: `navigator.deviceMemory`/`hardwareConcurrency` are useless (CPU/RAM proxies, privacy-rounded, GPU-blind); the correct 2025-2026 signal is a runtime rAF-FPS self-probe paired with the **Long Animation Frames API** (`PerformanceObserver`, Chrome 123+) to distinguish "main-thread JS is slow" from "frames drop with no attributable script" (the latter = compositor/raster-bound = our exact laptop case) — only the second case should trigger a cheap-render-mode, since throttling JS work wouldn't fix a compositor-bound bottleneck. No existing overdraw/fill-rate playbook translates cleanly to Canvas2D `drawImage`-of-bitmaps (literature is WebGL-centric); no 2025-2026 conference talk exists on this exact old-hardware-canvas-jank niche (confirmed gap, not a search miss). **Action item**: before committing further render-path fixes for the laptop pan case, run the `chrome://tracing` diagnostic to confirm the tile-eviction hypothesis — a render-path fix (quantization/DPR cap/tiling) may not move the needle if the root cause is VRAM-budget-driven, in which case the fix is elsewhere (reduce backing-store bytes per element, i.e. the DPR cap, or reduce simultaneously-resident tile count via viewport tiling).
